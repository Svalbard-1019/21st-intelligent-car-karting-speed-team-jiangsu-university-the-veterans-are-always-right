# 科目一高速追踪偏移代码审查

## 1. 问题说明

当前车辆在 1.0 m/s 以内能够正常跟踪记录路线，但速度提高到 1.5～2.5 m/s 后，会出现以下现象：

- 到达转弯附近后没有及时转向；
- 实车越过正常入弯位置后才开始打方向；
- 整体轨迹相对记录路线发生偏移；
- 不同弯道可能表现为前两个弯偏晚、后一个弯偏早；
- 修改预瞄和转向 PID 后，问题仍然存在。

编码器距离和 IMU 已经进行过单独测试，静态结果基本正常。本次审查不修改程序，只从完整控制链路查找所有可能原因。

当前审查版本：

```text
分支：codex/reverse-parking-test
提交：0c46707 Restore high speed tracking preset
```

## 2. 总体结论

最符合现象的主要原因不是单纯的转向 PID、GPS 或预瞄参数，而是下面两项叠加：

1. 主循环被串口输出和屏幕刷新拖慢后，单次编码器增量超过保护阈值，程序把这一整段里程直接清零。
2. 纯追踪得到转向目标以后，还要经过目标转角变化速度限制，方向盘无法立即打到算法要求的角度。

这会形成下面的因果链：

```text
串口和屏幕占用主循环时间
        ↓
两次 Encoder_Get() 的间隔变长
        ↓
高速时编码器增量超过 200
        ↓
该段编码器增量被直接清零
        ↓
INS 计算位置落后于实车位置
        ↓
程序认为车辆还没有到达弯口
        ↓
转向目标生成时间偏晚
        ↓
转向目标又被 3°/20ms 的变化速度限制
        ↓
实车继续前进 0.3～0.6m 后才完成转向
```

路线索引跳转、原始路线噪声、按点数预瞄以及新增后轮差动 PWM，会进一步放大不同弯道之间的偏差。

## 3. 第一优先级：高速时惯导可能丢失编码器增量

### 3.1 编码器增量保护阈值过小

位置：`code/peripheral.c`

```c
#define ENCODER_DELTA_ABS_MAX (200)
```

`Encoder_Get()` 中，如果两次读取之间的编码器差值超过 200，程序不会裁剪到 200，也不会分段处理，而是直接把本次增量设为 0：

```c
if(raw_delta_l > ENCODER_DELTA_ABS_MAX || raw_delta_l < -ENCODER_DELTA_ABS_MAX)
{
    count->delta_l = 0;
}
```

当前科目一里程系数为：

```c
#define ONE_TICK_DISTANCE 0.000473f
```

所以 200 个计数只对应：

```text
200 × 0.000473m = 0.0946m
```

不同速度下，主循环允许的最长停顿时间约为：

| 车速 | 200计数对应时间 |
|---|---:|
| 1.0m/s | 94.6ms |
| 1.5m/s | 63.1ms |
| 2.0m/s | 47.3ms |
| 2.5m/s | 37.8ms |

因此，编码器硬件本身即使完全正常，只要主循环在 2.5m/s 时有一次超过约 38ms 的停顿，这次约 9.5cm 的里程就会被丢弃。

### 3.2 串口输出时间已经接近或超过阈值

位置：`user/cpu0_main.c`

自动驾驶模式每 200ms 输出一次完整 `AUTO` 调试数据：

```c
#define SERIAL_DEBUG_PERIOD_MS (200)
```

当前调试行包含位置、航向、转向、GPS、停车、速度、编码器等大量字段。对现有记录统计后，每行平均约 483 字节。

调试串口为 115200 波特率。按每字节 10bit 计算，发送一行的理论时间约为：

```text
483 × 10 ÷ 115200 ≈ 41.9ms
```

底层 `uart_write_string()` 逐字节调用 `uart_write_byte()`。当发送数据超过硬件 FIFO 容量后，主循环需要等待串口继续发送。

41.9ms 已经超过车辆 2.5m/s 时允许的 37.8ms。再叠加 `sprintf()` 格式化和其他任务，很容易触发编码器增量清零。

### 3.3 屏幕刷新进一步占用主循环

位置：`user/cpu0_main.c`、`code/guandao.c`

自动驾驶过程中，主循环没有显示刷新周期限制，每轮都会重复显示：

- Idx、Len；
- 距离 D、角度 A；
- Reason；
- 左右目标速度；
- 目标速度、实际速度；
- PWM；
- Yaw；
- X/Y。

此外，`pursuit_contral_mode()` 内部每次计算还会执行：

```c
ips200_show_float(X(10), Y(9), target_steering, 5, 5);
```

这些函数会同步执行屏幕通信。即使屏幕损坏或没有正常显示，只要代码仍在调用，仍可能消耗主循环时间。

### 3.4 现有数据中的旁证

对现有高速运行记录进行计算，部分运行中根据 `x/y` 变化累计出的 INS 路程，比后轮累计编码器对应的路程少约 10%～12%。

这不能单独证明每一次都是增量阈值导致，但与“程序周期性漏掉一段里程”的表现一致。

## 4. 第二优先级：转向目标本身被限制得太慢

位置：`code/guandao.c`

当前转向目标变化速度参数为：

```c
#define GUANDAO_STEER_RATE_LOW  3.0f
#define GUANDAO_STEER_RATE_HIGH 3.0f
```

实际限制逻辑：

```c
float steer_delta_limit = steering_rate_limit * ((float)steer_elapsed_ms / 20.0f);
```

它表示每 20ms 最多改变 3°。因此目标角从 0°变化到 35°至少需要：

```text
35 ÷ 3 × 20ms ≈ 233ms
```

这 233ms 内车辆前进距离约为：

| 车速 | 转向目标从0°到35°期间前进距离 |
|---|---:|
| 1.0m/s | 0.23m |
| 1.5m/s | 0.35m |
| 2.0m/s | 0.47m |
| 2.5m/s | 0.58m |

因此，即使转向电机 PID 足够快，也只能跟随一个缓慢变化的目标。修改 PID 后晚转位置基本不变，是符合代码逻辑的。

## 5. 高速参数没有真正连续随速度变化

位置：`code/guandao.c`

当前代码按固定档位选择参数：

```c
if(base_speed > 5.0f)
{
    if(base_speed >= 15.0f)
    {
        // 高速参数
    }
    else if(base_speed >= 10.0f)
    {
        // 中速参数
    }
}
```

旧速度单位乘以 `0.1` 后才是 m/s，因此：

```text
base_speed=10 → 1.0m/s
base_speed=15 → 1.5m/s
base_speed=25 → 2.5m/s
```

1.5m/s 和 2.5m/s 都进入同一套 `base_speed >= 15` 参数。车速提高约 67%，但预瞄、转角增益和转向变化速度不会继续同比调整。

## 6. 预瞄使用点数，不是实际距离

位置：`code/guandao.c` 的 `pursuit_midhandle()`

```c
preview_index = state->current_point_index + index;
```

这里假设每个路线点之间距离一致。但实际记录点可能受到以下因素影响：

- 推车速度变化；
- 主循环刷新速度变化；
- 编码器增量被清零；
- 每次越过 `recode_threshold` 后只记录当前位置；
- 转弯时车轮滑动。

所以“预瞄5个点”不一定稳定等于1m。不同路段相同点数可能代表不同物理距离。

## 7. 最近点搜索可能跳过绕锥桶弧线

位置：`code/guandao.c` 的 `guandao_find_closest_index()`

当前会在 `current_point_index` 后面的8个点中寻找欧氏距离最近的点：

```c
#define GUANDAO_TRACE_SEARCH_POINTS 8
```

判断条件只考虑距离：

```c
if(distance + 0.05f < best_distance)
{
    best_index = i;
}
```

没有判断：

- 车辆是否已经沿路线经过该点；
- 路线切线方向是否和当前车头一致；
- 点是否位于车身前方；
- 是否跨过了圆弧或相邻路线。

绕锥桶、回头弯和路线相邻区域中，未来某个点可能在空间上更近，但沿路线还没有到达。高速时一次主循环跨过的距离更大，更容易发生索引跳跃。

## 8. 当前科目一没有使用平滑路线

当前串口数据中始终显示：

```text
plen=0
ready=0
```

`guandao_route_point()` 的逻辑是：

```c
if(state->plan_ready && state->planned_length > 0)
    return state->planned_map[index];
return state->recode_map[index];
```

因此目前科目一实际追踪的是原始 `recode_map`。虽然工程中存在 `guandao_build_smooth_plan()`，但当前自动驾驶启动流程没有启用平滑路线。

## 9. 急弯判断对单个异常点过于敏感

位置：`code/guandao.c` 的 `guandao_max_route_turn()`

当前算法检查未来12个点，并取其中最大的相邻线段航向变化：

```c
if(turn > max_turn) max_turn = turn;
```

只要一个记录点位置异常，就可能产生很大的局部转角，并触发：

- 急弯预瞄切换；
- 转角限幅切换；
- 55%急弯降速；
- 45%发卡弯降速。

现有串口数据里，`cturn10` 曾从约20°逐渐跳到170°以上，同时 `raw10` 出现正负方向切换。这说明原始路线局部几何、索引选择或两者组合存在不稳定情况。

## 10. 路线点推进存在同一周期数据不一致

在 `pursuit_contral_mode()` 中，程序先计算当前目标点的：

- `distance_to_target`；
- `angle_diff`。

如果距离达到阈值，会把 `current_point_index` 加一。但加一后没有重新计算当前目标点对应的 `angle_diff`，而预瞄点计算已经使用新的索引。

因此同一个控制周期内可能出现：

- 转向预瞄使用新索引；
- 部分减速判断仍使用旧目标点角度。

主循环足够快时影响较小；主循环因串口或屏幕阻塞而周期变长时，这种不一致会更明显。

## 11. 后轮差动 PWM 是当前版本新增的开环控制

位置：`code/rear_motor/rear_motor.c`

当前自动驾驶模式会根据左右目标速度差直接生成差动 PWM：

```c
float diff_val = out_v_l - out_v_r;
int16 diff_pwm = (int16)(diff_val * REAR_DIFF_PWM_GAIN);
```

差动最大可达到正负1500 PWM。

但当前后轮控制存在以下情况：

- 速度闭环使用左右平均目标速度；
- 实际速度反馈只使用一个编码器；
- 左右差动 PWM 没有独立左右轮闭环；
- 两个电机、轮胎负载和地面摩擦不一定一致。

因此差动 PWM 会改变车辆真实偏航特性，而且效果随速度、载重和地面变化。它不是原来高速能正常运行版本中的基础行为。

## 12. 前轮转角与后轮差速模型不一致

位置：`code/guandao.c`

前轮执行完整的 `target_steering`，但计算左右轮速度差时使用：

```c
tanf(target_steering / 3.0f)
```

也就是后轮差速模型只使用三分之一转角。若 `target_steering` 已经是实际前轮角度，那么车辆几何模型与实际转向执行不一致。

## 13. 后轮速度标定存在两种口径

位置：`code/rear_motor/rear_motor.c`、`code/rear_motor/rear_motor.h`

实际速度显示使用：

```c
REAR_SPEED_CALIBRATION_FACTOR = 0.7557f
```

但 PID 目标脉冲计算没有使用这个系数：

```c
float target_pulses = target_mps * 0.1f / REAR_DISTANCE_PER_PULSE_M;
```

这会导致：

- 显示的实际速度；
- PID的目标脉冲；
- 用户设置的目标 m/s；

不完全处于同一个标定体系中。它主要影响实际车速和降速效果，不是晚转的第一原因，但需要统一。

## 14. 转向目标被截断成整数

位置：`code/control.c`

```c
angle_control_set_target((int32)servo_out);
```

虽然 `angle_control_set_target()` 已经支持浮点数，但调用时仍强制转换成 `int32`。小于1°的目标变化会被截断，容易造成：

- 转向目标阶梯变化；
- 小角度修正不连续；
- 高频左右抖动；
- 低速回正不够丝滑。

它更能解释“转向像抖动一样不丝滑”，但不是高速整体晚转的首要原因。

## 15. GPS 对前段整体偏移影响较低

当前普通前进追踪中，`trace_gps()` 主要更新 GPS 辅助点状态和丢失判断，并不会持续修改：

```c
INS.current_state.x
INS.current_state.y
```

GPS坐标补偿主要在接近停车区域时用于倒车停车路线。因此：

- GPS可能影响最终停车位置；
- GPS辅助点不准可能影响局部判断；
- 但GPS很难单独解释所有弯道随速度提高而统一晚转。

## 16. IMU仍存在固定周期和比例误差风险

位置：`code/IMU.c`、`user/isr.c`

当前 Yaw 积分固定使用：

```c
Yaw_1 -= RAD_TO_ANGLE(IMU_Data.gyro_z * 0.00916f);
```

但 IMU 中断通过 `TIM_FLAG1 > 7` 触发，名义调用周期更接近8ms。当前工作区角速度换算除数为 `15.9`，不是之前讨论的 `14.3`。

此前90°旋转显示约100°，已经说明航向比例仍有约10%的误差。

这项误差不是最符合“低速正常、高速晚转”的主因，但会放大转弯角度误差，后续仍应单独标定真实调用周期和比例系数。

## 17. 建议的逐项验证顺序

后续修改应一次只验证一个变量，避免继续同时调整 PID、预瞄、速度和停车逻辑。

### 第一步：验证主循环是否丢编码器增量

需要记录：

- 每次 `Encoder_Get()` 的实际间隔；
- `raw_delta_l`；
- 超过200的次数；
- 被清零的累计计数；
- 主循环最长执行时间。

如果高速运行中出现 `raw_delta_l > 200`，就可以直接确认惯导漏里程。

### 第二步：隔离串口和屏幕负载

保持路线、速度、PID和预瞄完全不变，只分别测试：

1. 当前完整调试输出；
2. 暂停屏幕实时刷新；
3. 缩短串口字段或降低输出频率；
4. 串口和屏幕都不参与控制主循环。

观察相同速度下入弯位置是否恢复。

### 第三步：验证目标转向限速

记录以下时间点：

- `raw10` 首次明显变化；
- `fin10` 首次明显变化；
- `servo10` 首次明显变化；
- `steerA10` 实际角度开始变化；
- 到达目标角的时间。

这样可以分开判断：

```text
路线算法晚发现弯道
还是
算法已经要求转弯，但限速器/PID/机械执行晚了
```

### 第四步：暂时隔离后轮差动 PWM

保持中心速度不变，分别比较：

- 左右后轮相同 PWM；
- 当前差动 PWM。

确认差动控制是在帮助转向，还是使车辆实际轨迹进一步偏离模型。

### 第五步：检查路线点和索引

在串口中增加：

- 当前索引；
- 最近点搜索前后的索引；
- 转向预瞄点索引与坐标；
- 曲率预瞄点索引与坐标；
- 相邻点实际距离；
- 当前点切线方向。

重点检查绕锥桶时是否跨过圆弧点或跳到空间上更近、但路线顺序更靠后的点。

### 第六步：最后再调整预瞄和 PID

只有确认以下条件成立后，调整预瞄和 PID 才有意义：

- 惯导没有丢里程；
- 控制周期稳定；
- 路线索引没有错误跳转；
- 转向目标产生时间正确；
- 后轮实际运动与模型一致。

否则继续修改 PID 或预瞄，只是在补偿一个随速度变化的时序和定位错误，很难得到普适参数。

## 18. 当前问题优先级

| 优先级 | 可疑问题 | 与高速晚转的相关性 |
|---|---|---|
| P0 | 主循环阻塞后编码器增量超过200并清零 | 极高 |
| P0 | 转向目标3°/20ms限速 | 极高 |
| P1 | 屏幕无周期限制刷新 | 高 |
| P1 | 最近点搜索在圆弧附近跳点 | 高 |
| P1 | 1.5～2.5m/s共用同一高速参数 | 高 |
| P1 | 原始路线未平滑、局部曲率异常 | 高 |
| P1 | 后轮差动PWM没有左右独立闭环 | 中高 |
| P2 | 按点数预瞄而非距离预瞄 | 中高 |
| P2 | 转向目标被截断为整数 | 中 |
| P2 | 后轮速度标定口径不统一 | 中 |
| P2 | IMU积分周期和比例系数误差 | 中 |
| P3 | GPS辅助点误差 | 前段低、停车段较高 |

## 19. 最终判断

当前最应该先证明或排除的是“高速时主循环停顿导致编码器增量被清零”。它同时满足以下特征：

- 与速度强相关；
- 低速基本正常；
- 高速时INS位置落后于实车；
- 表现为到弯口后才转向；
- 编码器单独测距离仍可能正常；
- 调整预瞄和PID不能稳定解决；
- 最近增加的大量串口字段会进一步恶化问题。

在这个问题确认之前，不建议继续同时修改高速预瞄、转向 PID、转角限幅和降速比例。
